# v0.2.3 — S0 Runner-Clock Correction Candidate

> **Status: not published; not independently re-audited; S0 remains failed/blocked.** This candidate supersedes the flawed v0.2.2 remediation candidate after a post-merge review found S0-003.

## S0-003: what was wrong in v0.2.2

The v0.2.2 S0-001 remediation correctly removed the caller-controlled `segment.created_at` fallback and required a trusted admission clock. However, `ScenarioRunner` initialized that controlled clock at a fixed `2026-01-01T00:00:00Z`. Scenario fixtures issue provenance at deterministic scenario-index offsets in whole seconds, with delayed material one second later. For nonzero-index scenarios, the runner clock remained earlier than fixture issuance and valid segments were rejected as `attestation_not_yet_valid`.

This was reproduced on `protected_remote` with the `admission_only` adapter: every initial fixture segment and the delayed segment was rejected despite valid verifier-issued provenance. The resulting run still completed, showing why end-to-end admission assertions are necessary in addition to run/replay checks.

## Correction

`ScenarioVariant` now carries a `runtime_start` field created by the trusted scenario harness. It is deterministically two seconds after that catalog fixture set's latest issuance time and is not read from a submitted segment or attestation. `ScenarioRunner` initializes its `ControlledClock` from this field. Admission therefore still uses a runner-owned controlled clock, while valid initial and delayed fixture attestations are evaluated after issuance.

The harness identity is `2.0.2`; the package version is `0.2.3`. The adapter remains `2.0.1` because its required-clock API did not change in this corrective patch.

## New regression coverage

The corrected candidate adds an end-to-end lifecycle test using `protected_remote`, a nonzero-index scenario. It asserts that the trusted runtime start is later than every initial and delayed provenance issuance time, that all initial fixture segments are admitted, and that the delayed fixture segment is admitted at its scheduled turn. Existing S0-001 tests continue to prove that expired/future attestations with attacker-chosen segment timestamps reject, and S0-002 tests continue to prove that external `active_invariant` metadata receives no compaction protection.

## Internal remediation evidence

The correction branch completed the following local checks before protected review: **128 tests passed** with 92% diagnostic coverage; Ruff formatting/lint and strict Mypy passed; the local example and simulator observe/warn/enforce demo passed; a fresh four-run smoke stage completed with harness version 2.0.2; the fresh artifact set passed passive audit with no errors/warnings; and all **4/4** fresh traces replayed through the project CLI. These are local deterministic remediation checks, not an independent audit decision.

## Required focused re-audit

The independent re-auditor must review the final merged v0.2.3 correction commit and test all of the following.

1. S0-001: expired and future attestations cannot choose lifecycle time through submitted segment fields; every direct and adapter call requires trusted runtime time.
2. S0-002: metadata cannot create compaction residency; verified principal required constraints remain protected.
3. S0-003: nonzero-index scenarios and delayed material are admitted when their valid verifier-issued attestations are evaluated against the runner-owned runtime start.
4. The runner start is controlled by trusted harness/catalog state, not read from segment or attestation fields supplied to admission.
5. Full test, static, smoke, passive-audit, and replay gates run from a clean checkout.

A green internal gate, deterministic replay, CI check, or automated review is remediation evidence only. The final S0 gate remains failed until the independent reviewer returns a written Pass or appropriately bounded Conditional Pass with no unresolved Critical or High finding.
